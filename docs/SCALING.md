# SCALING — 데이터가 쌓일 때의 업그레이드 가이드 (v2 설계도)

> 이 대시보드는 무백엔드 단일 HTML이다. 데이터(문의 로그 push, 카드의 AI 참조 로그 텍스트)가 누적되면 브라우저가 무거워질 수 있다.
> 이 문서는 **언제(임계점) · 무엇을 · 어떻게** 업그레이드하는지의 설계도다. 임계점에 도달하면 AI에게 이 문서를 근거로 v2를 생성하게 하면 된다.
> 핵심 전제: 이 시스템은 **모든 작업을 AI에 위임하고 사람은 감독**하는 운영을 가정한다. 따라서 모든 최적화는 **AI의 맥락 접근을 끊지 않아야** 한다.
> ✅ **검증됨**: 이 설계도의 단계 A·B와 헬퍼(`--compact`/`--archive-before`)는 [`demo-v2/`](../demo-v2/)에 대량 허구 데이터(315건/891 push)로 실제 구현·검증돼 있다.

---

## 0. 핵심 원칙 — "표시는 분리, 검색은 통합" (Render local, search global)

브라우저 화면(사람)에서만 과거 데이터를 숨겨 성능을 확보한다. **AI의 데이터 접근은 항상 전체를 포괄**한다. 이 한 원칙이 모든 단계를 지배한다.

왜 이렇게 해도 AI에 병목·혼선이 없는가:

1. **지식의 정본은 로그가 아니다.** 처리 이력(`inquiry-log.js`)은 로그일 뿐, 진짜 지식(절차·교훈·방침)은 지식 아카이브(예: `archive.html`)·카드의 AI 로그(`ailog`)·AI 메모리에 영속한다. 완료 항목을 로그에서 분리해도 **AI의 지식 접근은 무손실**이다.
2. **Grep은 파일 개수와 무관하게 전부 훑는다.** 과거를 `inquiry-log-archive-*.js`로 분리해도 와일드카드 검색으로 활성+아카이브를 한 번에 찾는다.
3. **활성 파일이 작아져 AI의 일상 읽기가 가벼워진다(토큰↓).** 최적화는 오히려 AI에 유리하다.

---

## 1. 임계점 — 언제 무엇을 한다

| 데이터 규모 | 증상 | 적용할 단계 |
|---|---|---|
| ~수십 건 (현재) | 없음 | **아무것도 하지 않는다** (조기 최적화 회피) |
| 완료 100건+ | 첫 로드가 약간 느려짐 | **단계 A** (ailog 지연 렌더) → **단계 B** (완료 아카이브 분리) |
| 수천 건 | 로그 파일이 수 MB, DOM 노드 과다 | **단계 C** (로그 컴팩션) → **단계 D** (완료 열 가상 스크롤) |

원칙: **한 단계씩**, 증상이 실제로 보일 때만. 측정 없이 미리 다 하지 않는다.

## 2. 단계별 설계 (v2 구현 명세)

### 단계 A — AI 참조 로그(ailog) 지연 렌더  ★가성비 최고, 부작용 없음
**문제**: 카드의 `ailog`는 접혀 있어도 텍스트가 DOM에 전부 존재 → 카드 수백 개면 노드·문자열 폭증.
**해법**: ailog 텍스트를 처음엔 DOM에 넣지 않고, `<details>`를 펼칠 때 1회 주입.

```js
// 카드 렌더 시: ailog 본문을 DOM에 넣지 말고 데이터만 보관
//   <details class="ailog" data-ailog-id="DEV-003"> ... <div class="ailog-body"></div></details>
const AILOG = {};                       // id -> ailog 텍스트 (TASKS/로그에서 채움)
document.querySelectorAll('details.ailog').forEach(d => {
  d.addEventListener('toggle', () => {
    const body = d.querySelector('.ailog-body');
    if (d.open && !body.dataset.filled) {
      body.textContent = AILOG[d.dataset.ailogId] || '';
      body.dataset.filled = '1';        // 1회만 주입
    }
  });
});
```
**AI 영향**: 없음. AI는 DOM이 아니라 소스 파일(tasks.md / TASKS 배열)을 읽으므로 ailog 데이터는 그대로 접근 가능.

### 단계 B — 완료 항목 아카이브 분리  ★파일 크기 최대 절감
**문제**: append-only 로그가 무한 증가 → 매 로드마다 전체 다운로드·파싱.
**해법**: 완료 후 일정 기간 지난 항목을 반기별 아카이브 파일로 분리. 화면은 활성만 로드, 과거는 버튼으로.

- 네이밍(필수): `inquiry-log.js`(활성) + `inquiry-log-archive-2026H1.js`(과거). **포맷·push 구조 동일** → Grep/파싱 호환.
- `task-board.html`: 기본은 활성만 로드. 「과거 이력 보기」 버튼 → 아카이브 js를 동적 `<script>`로 주입 후 재렌더.
- **`metrics`(실증지표)·책 소재 집계는 활성+아카이브 전체 합산** (누적 지표라 과거가 빠지면 숫자가 줄어든다).
- 헬퍼에 분리 명령 추가:

```bash
# 완료 상태 + 지정일 이전 항목을 아카이브 파일로 이동(활성에서 제거)
python log-inquiry.py --archive-before 2026-07-01   # → inquiry-log-archive-2026H1.js 생성/추가
```
**AI 영향 차단(가드레일)**:
- 과거 이력 검색은 항상 `inquiry-log*.js` 전체를 대상으로 한다(와일드카드 Grep).
- 완료 기록(쓰기)은 **항상 활성 파일에만** append.
- AGENTS.md/CLAUDE.md에 위 두 줄을 명시한다.

### 단계 C — 로그 컴팩션
**문제**: 같은 id에 상태 전이 push가 여러 개 누적(접수→진행중→대기→완료) → 줄 수 폭증.
**해법**: 같은 id의 여러 push를 **현재 상태 1줄**로 병합한 스냅샷으로 재작성. append-only의 동시기록 안전성은 유지하되, 조용한 시점에만 실행.

```bash
python log-inquiry.py --compact          # 같은 id push들을 최신 병합 1줄로 압축
python log-inquiry.py --compact --keep-history   # 시계열 보존이 필요하면 별도 파일로 백업
```
**주의**: 중간 시계열(단계별 로그)에 교훈이 있으면 카드 `ailog`·지식 아카이브·메모리에 이미 보존돼 있어야 한다(컴팩션 전에 확인). 로그는 "상태", 지식은 "아카이브"가 정본.

### 단계 D — 완료 열 가상 스크롤 / "최근 N개 + 더보기"
**문제**: 완료 카드 수백 개를 한 번에 DOM에 그림.
**해법**: 화면에 보이는 카드만 렌더. 가장 단순한 형태는 완료 열 기본 "최근 30개" + 「더보기」로 증분 렌더(가상 스크롤의 경량 대체).

---

## 3. AI에게 업그레이드를 시키는 법

1. 트리거: **"대시보드 v2 업그레이드"** 또는 **"임계점 넘었으니 최적화"**.
2. AI는 이 `SCALING.md` + 현재 데이터 규모를 보고 **해당 단계만** 적용한다(임계점 표 기준).
3. 각 단계 적용 후 **가드레일 체크리스트**(아래)를 통과해야 완료로 본다.
4. 변경은 `CHANGELOG.md`에 기록한다(날짜·단계·영향 파일).

### 가드레일 체크리스트 (단계 B 이후 필수)
- [ ] 아카이브 파일이 활성과 **같은 포맷·네이밍**인가 (`inquiry-log-archive-*.js`)
- [ ] 과거 이력 검색이 `inquiry-log*.js` **전체**를 대상으로 하는가
- [ ] 완료 기록(쓰기)이 **활성 파일에만** 가는가
- [ ] `metrics`·집계가 **아카이브 포함 전체**를 합산하는가
- [ ] AGENTS.md/CLAUDE.md에 위 규칙이 명시돼 있는가

> 이 체크리스트를 통과하면, 데이터가 아무리 쌓여도 **사람 화면은 가볍고 AI 맥락은 온전**하다. 그게 이 문서의 목적이다.
